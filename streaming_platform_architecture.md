# Streaming Platform Backend Architecture & Specifications (v2)

This document outlines the complete system architecture, database schemas, caching strategies, API contracts, and operational workflows for building a private, invite-only movie/TV streaming platform utilizing third-party embed providers (e.g., VidSrc, SuperEmbed).

Designed for **< 100 users**, prioritizing **zero hosting costs**, operational simplicity, high performance, and resilience.

---

## 1. Core System Architecture

The platform operates as a **modular monolith** built on **Next.js (App Router)** hosted on **Vercel**. It functions strictly as a high-performance metadata catalog, identity/access manager, and embed router — **never as a media host or CDN**.

### Zero-Cost Stack Breakdown

| Component | Technology | Free Tier Allocation | System Consumption (< 100 users) |
|---|---|---|---|
| **App & API** | Next.js on Vercel | 100 GB bandwidth, 100k executions/mo | Minimal execution overhead, fast edge routing |
| **Database** | MongoDB Atlas (M0) | 512 MB storage, shared cluster | Text data + indexes < 20 MB |
| **Cache & Rate Limit** | Upstash Redis | 10,000 commands/day, 256 MB | REST client; cached reads ensure < 5k cmds/day |
| **Metadata Source** | TMDb API | Free with attribution | Heavily cached via Redis Cache-Aside |
| **Cross-Watch Sync** | Simkl API | Free OAuth2 access | Fire-and-forget sync on status changes |
| **CI/CD** | GitHub Actions | 2,000 build mins/mo | Automated lint, typecheck & Vercel deployment |

> [!IMPORTANT]
> **Serverless Environment Considerations**:
> - **Connection Management**: MongoDB connections must be cached across hot lambdas using a global client singleton. Redis uses `@upstash/redis` (stateless HTTP/REST) rather than persistent TCP sockets.
> - **Background Tasks**: Long-running background daemons cannot run inside serverless functions. Instead, recurring maintenance runs via **Vercel Cron Jobs** (e.g., telemetry processing, health checks).
> - **Live State**: Video progress and "Continue Watching" sync run via lightweight debounced REST requests during playback.

## 2. Authentication & Access Control

### Single-Use Invite Code System
The platform is strictly private. Open registration is disabled. To join, a user must possess a valid, unused invite code generated by an admin.

```
┌────────────────┐     Generates Code      ┌──────────────────┐
│  Admin Panel   │ ──────────────────────► │   invite_codes   │
└────────────────┘                         │ (Status: active) │
                                           └────────┬─────────┘
                                                    │ User registers
                                                    ▼
┌────────────────┐    Issues JWT Tokens    ┌──────────────────┐
│ /api/auth/me   │ ◄────────────────────── │   invite_codes   │
│ (Active User)  │                         │  (Status: used)  │
└────────────────┘                         └──────────────────┘
```

### JWT Token Architecture
1. **Access Token**: Short-lived (15 minutes), passed via `Authorization: Bearer <token>` header, held in frontend application state/memory.
2. **Refresh Token**: Long-lived (7 days), stored in an `httpOnly`, `secure`, `SameSite=Strict` cookie (`/api/auth/refresh`).
3. **Role-Based Authorization**:
   - `user`: Browse catalog, request streams, manage watchlists, sync with Simkl, report stream failures.
   - `admin`: All user capabilities + invite code generation/revocation, provider registry management, telemetry analytics, and user account management (enable/disable).

## 4. Caching & Metadata Layer (Upstash Redis)

### Cache-Aside + SWR Strategy
All metadata requests query Upstash Redis first. On a cache miss, data is fetched from TMDb, filtered through an adapter to remove redundant payload bloat, stored in Redis with a type-specific TTL, and returned to the client.

```
Incoming Request
      │
      ▼
Check Upstash Redis
 ├── HIT ──► Return transformed JSON payload
 └── MISS ─► Fetch TMDb API ──► Strip fields (Adapter) ──► Write to Redis (with TTL) ──► Return JSON
```

### Key Naming Conventions & TTL Matrix

| Data Target | Redis Key Pattern | TTL | Invalidation Trigger |
|---|---|---|---|
| **Movie Metadata** | `tmdb:movie:{tmdbId}` | 30 Days (Old) / 12 Hours (New) | Cache expiration |
| **TV Show Metadata** | `tmdb:tv:{tmdbId}` | 4 Hours (Ongoing) / 14 Days (Ended) | Cache expiration |
| **TV Season Details** | `tmdb:tv:{tmdbId}:s{seasonNum}` | 24 Hours | Cache expiration |
| **Search Queries** | `tmdb:search:{queryHash}` | 6 Hours | Cache expiration |
| **Trending Feeds** | `tmdb:trending:{mediaType}:{window}` | 1 Hour | Revalidation cron/read |
| **Discovery/Genres** | `tmdb:genres:{mediaType}` | 7 Days | Cache expiration |
| **Computed Streams** | `streams:{mediaType}:{tmdbId}` | 5 Minutes | Provider health score update |

### Stripped Metadata Adapter Example
Never store multi-kilobyte raw TMDb responses. Cache only display-critical attributes:

```typescript
// Adapter transformation before caching in Redis
export function transformMovieMetadata(raw: any) {
  return {
    tmdbId: raw.id,
    imdbId: raw.imdb_id,
    title: raw.title,
    originalTitle: raw.original_title,
    overview: raw.overview,
    posterPath: raw.poster_path,
    backdropPath: raw.backdrop_path,
    releaseDate: raw.release_date,
    runtime: raw.runtime,
    genres: raw.genres?.map((g: any) => ({ id: g.id, name: g.name })) || [],
    voteAverage: Math.round(raw.vote_average * 10) / 10,
    status: raw.status,
    tagline: raw.tagline,
    _cachedAt: new Date().toISOString()
  };
}
```

### Fail-Open Resilience
If Upstash Redis is unreachable or rate-limited:
1. Log an internal warning.
2. Directly query TMDb.
3. Serve the response without blocking user interaction (fail-open mode).

## 6. Embed Router & Fallback Mechanics

### URL Generation Engine
When a client requests stream options for a title, the embed router:
1. Queries the `providers` collection for documents where `isEnabled: true` and `circuitBreakerTripped: false`.
2. Filters by `supportedTypes` matching the target media.
3. Sorts candidates by `healthScore DESC, priority ASC`.
4. Dynamically substitutes route parameters into the stored pattern templates.

```typescript
export function constructEmbedUrl(
  provider: ProviderDoc,
  mediaType: "movie" | "tv",
  tmdbId: number,
  season?: number,
  episode?: number
): string | null {
  const pattern = provider.urlPatterns[mediaType];
  if (!pattern) return null;

  return provider.baseUrl + pattern
    .replace("{tmdbId}", String(tmdbId))
    .replace("{season}", String(season ?? 1))
    .replace("{episode}", String(episode ?? 1));
}
```

### Client-Side Fallback Strategy ("Waterfall" Player)
Since third-party iframes cross domain boundaries, the frontend player monitors:
- **Iframe `onerror` event**
- **Load Timeout (10 seconds)**: If player state has not transitioned, flag as degraded.
- **Manual Fallback**: User clicking "Switch Server" button triggers client telemetry report and loads next index in the `streams` array automatically.

```
Load Stream[0] (Highest Health)
       │
       ├─► Playback succeeds ──► Log continuous watch progress
       │
       └─► Fails / Times out ──► POST /api/telemetry/embed-failure
                                 Load Stream[1] (Next candidate)
```

## 7. Automated Circuit Breaker & Health Scoring

### Calculation Formula
Executed every 15 minutes by Vercel Cron (`/api/cron/update-provider-health`):

$$\text{healthScore} = \max\left(0, 100 - (\text{failures}_{24\text{h}} \times 2)\right)$$

### Circuit Breaker Rules
- If $\text{healthScore} < 30$: Trip circuit breaker (`circuitBreakerTripped = true`). The provider is excluded from stream resolution.
- If no new failures occur in a 6-hour window: Reset circuit breaker to test recovery (`circuitBreakerTripped = false`, probationary health = 50).

## 8. Simkl Integration Architecture

### OAuth2 Linking Flow
```
User clicks "Connect Simkl"
  │
  ├─► Redirects to https://simkl.com/oauth/authorize
  │
  └─► Callback to /api/auth/simkl/callback?code=XYZ
        │
        ├─► Exchanges code for access_token + refresh_token
        │
        └─► Saves credentials in user.simklToken
```

### Fire-and-Forget Sync
Whenever a user marks media as `completed`, changes status, or updates watch progress past 90%:
1. Local MongoDB `user_activities` updates immediately.
2. An asynchronous background dispatch pings Simkl's `/sync/history` API using the stored `simklToken`.
3. If the token is expired, silent refresh is attempted; if invalid, notify the user on settings page without breaking local playback.

## 9. Security Hardening & Rate Limiting

### Input Validation
All request bodies and query parameters pass through strict **Zod schemas**. Invalid payloads are rejected with `400 Bad Request` before hitting controllers.

### Rate Limiting (Upstash Serverless Ratelimit)
Using sliding window algorithms:

| Endpoint Group | Threshold | Window |
|---|---|---|
| `/api/auth/login` | 5 requests | 15 Minutes (IP-based) |
| `/api/auth/register` | 3 requests | 1 Hour (IP-based) |
| `/api/content/*` | 60 requests | 1 Minute (User-based) |
| `/api/streams/*` | 30 requests | 1 Minute (User-based) |
| `/api/telemetry/*` | 10 requests | 1 Minute (User-based) |

### Security Headers (`next.config.js`)
```javascript
const securityHeaders = [
  { key: "X-Content-Type-Options", value: "nosniff" },
  { key: "X-Frame-Options", value: "DENY" },
  { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
  { key: "Permissions-Policy", value: "camera=(), microphone=(), geolocation=()" }
];
```

## 12. CI/CD Pipeline (GitHub Actions)

```yaml
name: CI & Deployment Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  validate:
    name: Lint, Typecheck & Test
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Setup Node.js 20
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'

      - name: Install Dependencies
        run: npm ci

      - name: Run ESLint
        run: npm run lint

      - name: Run TypeScript Typecheck
        run: npm run type-check

  deploy:
    name: Deploy to Vercel
    needs: validate
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Deploy to Vercel Production
        uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
          vercel-args: '--prod'
```

## 13. Summary of Improvements (v1 vs. v2)

| Dimension | Initial Spec (v1) | Production Architecture (v2) |
|---|---|---|
| **Access Control** | Open user table with simple hash | Single-use admin invite code onboarding + JWT access/refresh rotation |
| **API Contract** | 1 unversioned endpoint mentioned | 25+ fully defined REST endpoints with request/response envelopes |
| **Provider Logic** | Static hardcoded link generator | Dynamic, database-driven provider registry with URL templates and capability tags |
| **Telemetry & Resilience** | Basic manual failure logs | Automated canary detection, 15-min cron health calculation, and circuit breaker |
| **Infrastructure** | Undefined server model | Zero-cost serverless stack (Next.js on Vercel + Upstash Redis + MongoDB Atlas) |
| **User Experience** | Single timestamp tracker | Resume point tracking, favorite tagging, and Simkl bidirectional sync |
| **Search & Discovery** | Unaddressed | Proxied TMDb search with debouncing, Redis caching, and composite feed loaders |
| **Security** | None specified | Zod validation, HTTP security headers, Upstash rate limiters, role-based gates |
| **DevOps** | Undefined | GitHub Actions CI/CD with automated validation and zero-downtime Vercel deployment |
